## Failures and causes

1. Playwright hung with no output (setup project, first attempt, over 8 minutes). Cause class: environment/tooling, not the app. Playwright empties its output folder `test-results/` at start, and the log files being written inside that folder blocked it on Windows (the runner never spawned a worker). Fix: `--output=test-results/pw-artifacts` so Playwright cleans a different folder; logs stay in `test-results/logs/`. No code change.
2. categories.spec.ts, 5 of 5 failed in the first attempt (401 on the first API call, redirect to `/login?returnTo=...`). Cause class: (d) API-side behaviour, plus test ordering. The QA API accepts one live session per account: the guest project logs in and out with the same shared admin account (auth.spec.ts "QA API" tests), which invalidates the token that `setup` saved earlier (the JWT itself was not expired, exp was 24 h ahead). The app behaved correctly (401 sent the user to login with returnTo). Fix: order of the runs, not code or assertions. Run `guest` and `mocked` first, then `setup`, then the chromium specs. Re-running `setup` and then the file gave 5 passed. Request seen: any authenticated GET, status 401, standard error envelope (no body details recorded).
3. Earlier known failure (products-list CSV export, Expected 1711, Received 1): the spec fix (wait for the filtered list before reading the total) is now proven by a live pass.

### Failure: image upload blocked by S3 CORS (storage side, not the app)
- Flow: `POST /utils/upload-file-urls` answered; the browser then did `PUT https://talking-club-dev.s3.ap-northeast-2.amazonaws.com/products/<key>/hw3-product-small.png?X-Amz-...` (signed URL, headers content-type, x-amz-acl, x-amz-checksum-crc32, x-amz-sdk-checksum-algorithm).
- Browser error: "blocked by CORS policy: Response to preflight request doesn't pass access control check: No 'Access-Control-Allow-Origin' header is present". The product form then never shows "Remove image 1:" and the spec fails.
- Preflight probed outside the browser (OPTIONS, Access-Control-Request-Method PUT, same headers):
  - Origin `http://localhost:3100` -> 403 `AccessForbidden`, "CORSResponse: This CORS request is not allowed" (no CORS headers).
  - Origin `https://tkclub-admin-qa.dvconsulting.org` -> 403, same.
  - Origin `http://localhost:3000` -> 200, `Access-Control-Allow-Origin: http://localhost:3000`, Allow-Methods `HEAD, PUT, POST, DELETE, GET`, Allow-Headers `content-type, x-amz-acl, x-amz-checksum-crc32, x-amz-sdk-checksum-algorithm`, Allow-Credentials true.
- Cause: the bucket `talking-club-dev` whitelists only `http://localhost:3000` (and not the QA admin origin). The app sends exactly the headers the bucket allows, so the app is correct. The upload cannot be proven from port 3100; nothing was mocked or faked.
- To prove it: run the same spec from an app on port 3000 (stop the other app first, Neeraj's decision), or ask the backend team to add the origin to the bucket CORS. Note for the deployed app: the QA admin origin is refused too, so image upload would fail there as well.
- Not proven live: product register / edit / delete (the failure happens in step 2 of the form, before anything was created, so nothing was written).
